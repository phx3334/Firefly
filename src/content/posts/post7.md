## 定位
HTTP 是应用层、请求-响应式的资源传输协议，定位为"定义 Web 通信语义"，可靠性和路由完全委托给下层（TCP 或 UDP/QUIC + IP）。   
它之所能不断演进（1.0→1.1→2→3），正是因为把"传什么/怎么传"和"怎么可靠送达"解耦了——换底层（TCP↔UDP）不影响它上层的语义。  
## http1.1
### 简单描述
| 改进点 | 说明 |
| --- | --- |
| 持久连接 keep-alive | **默认开启**，一条 TCP 连接可复用传多个请求/响应，省去重复握手（呼应 FAQ 里"为什么高并发用长连接"） |
| 强制 Host 头 | 支持虚拟主机，一个 IP 承载多个站点 |
| 分块传输 chunked | `Transfer-Encoding: chunked`，未知长度也能流式边生成边发 |  
### 痛点
`1`**应用层队头阻塞（HOL）**：keep-alive 虽复用连接，但响应仍默认串行返回——同一连接上，前一个响应没传完，后面的就只能排队。管线化想缓解却因支持差基本失效。  
`2`**多连接开销**：为并发，浏览器通常开 6~8 个 TCP 连接，每个都要三次握手 + 慢启动（呼应 上一篇"每次握手/拥塞窗口重新慢启动，高频小请求吞吐低"）。  
`3`**头部冗余未压缩**：每个请求都重复携带 Cookie、User-Agent、Accept 等大段文本头部，浪费带宽，移动端尤其明显。  
`4`**文本协议**：解析效率低于二进制，且易出错。  
`5`**TCP 层队头阻塞**：一个 TCP 包丢失，整条连接所有请求都要等它重传——这是传输层问题，HTTP/1.1 自身无解。  


## http/2
### 解决了哪些 1.1 痛点，怎么解决的
| HTTP/1.1 痛点 | HTTP/2 解法 |
| --- | --- |
| 应用层队头阻塞（响应串行） | **多路复用**：一个 TCP 连接上开多个**流（Stream）**，帧带 stream ID 交错发送，互不阻塞 |
| 多连接开销（开 6~8 条 TCP） | **单连接多路复用**，只需一条 TCP 连接，省掉重复握手与慢启动 （本质上和上一点解决方法一致）|
| 头部冗余未压缩 | **HPACK 头部压缩**：静态+动态字典，只传差量，大幅缩小重复首部 |
| 文本协议解析慢 | **二进制分帧**：数据切成二进制帧，解析高效、不易出错 |
| 无优先级 | **流优先级**：给流设依赖与权重，重要资源（CSS）优先传 |
### HTTP/2 还有什么痛点
`1`**TCP 层队头阻塞仍在**（最关键）：多路复用只解决了应用层，底层还是一条 TCP 连接——只要有一个包丢失，整条连接所有流都得等它重传（呼应上一篇 FAQ 里 TCP 重传 / seq 机制）。丢包网络下，多路复用的优势反而被抵消。  
`2`**建连延迟**：仍需先 TCP 握手 + TLS 握手，高 RTT 网络首字节延迟明显。  
`3`**单连接集中风险**：所有请求挤在一条 TCP 上，该连接一旦丢包 / 重置，影响面是全部请求；且拥塞窗口、RTT 是整条连接共享的。  


## http/3
### 解决了哪些痛点（对照 HTTP/2）
| 遗留痛点（来自 H2） | HTTP/3 解法 |
| --- | --- |
| TCP 层队头阻塞：一个包丢，整条连接所有流卡住 | **QUIC 按流独立可靠**：单流丢包只重传该流，其他流继续 |
| 建连延迟：TCP 握手 + TLS 握手叠加 | **0/1-RTT 握手**：传输握手与 TLS 1.3 融合，重连可达 0-RTT |
| 单连接集中风险：TCP 四元组绑定，IP 变就断 | **连接迁移**：用连接 ID 标识，切网不断连 |  
### 怎么解决的（核心：QUIC over UDP）
`1`**把可靠传输从 TCP 搬到 UDP 之上**：QUIC 在 UDP（只做尽力投递）之上，重做了 TCP 原本的职责——确认、重传、拥塞控制、多路复用，但粒度从"全局字节流"改为"按流"。    
`2`**多路复用 + 无队头阻塞**：连接上多个流各自独立有序交付；某流丢包，QUIC 只重传该流数据，其余流不受影响（对比 TCP 全局有序字节流，一处丢包全连接停顿——呼应 TCP 重传 / seq 机制）。   
`3`**0-RTT / 1-RTT 建连**：QUIC 将传输层握手与 TLS 1.3 加密握手合并。首次连接 1-RTT，复用缓存密钥重连可达 0-RTT，省掉 H2 的"TCP 握手 + TLS 握手"两轮。  
`4`**连接 ID（CID）实现连接迁移**：数据包携带连接 ID 而非依赖四元组。手机从 WiFi 切到 4G（IP 变）时 CID 不变，连接不中断——直接克服 TCP 四元组绑定的脆弱性（呼应上一篇FAQ 里"四元组""TIME_WAIT 禁止复用相同四元组"）。  


## 全面认识QUIC
`定位`QUIC 是基于 UDP 的传输层协议（RFC 9000），HTTP/3 直接以它为底层。它把 TCP 原本的职责（可靠、重传、拥塞控制、多路复用）在 UDP 之上重新实现，并补上 TCP 做不到的两件事：**按流独立可靠**与**连接迁移**。  

### 为什么在 UDP 之上重建，而不是直接改 TCP
`1`**TCP 僵化**：实现固化在内核，任何改进都要改操作系统、等全网设备升级，推进极慢；UDP 是空白画布，QUIC 在用户态迭代即可。  
`2`**中间设备歧视**：防火墙/NAT 常深究 TCP、甚至拦掉带未知 TCP 选项的包；QUIC 跑在 UDP 443 端口、伪装成普通流量，反而更少被误解。  
`3`**加密必选**：QUIC 内置 TLS 1.3，包头（除 CID 等少量字段）加密，防窥探/篡改；而 TCP 头部是明文，易被中间设备干扰。  

### 核心机制
`1`**多路复用 + 按流独立可靠**：一条连接开多个 Stream，流内有序可靠、流间独立；数据装为 STREAM 帧（带 Stream ID + 偏移），某流丢包只重传该流偏移区间，其余流照常交付（解决 TCP 全局队头阻塞）。  
`2`**连接 ID（CID）实现迁移**：包用 CID 而非四元组关联连接，切网 IP 变 CID 不变，连接不中断（克服 TCP 四元组绑定）。  
`3`**0-RTT / 1-RTT 建连**：传输握手与 TLS 1.3 融合，首次 1-RTT，复用缓存密钥重连 0-RTT。  
`4`**双层流控**：连接级 + 流级接收窗口，单流拥塞不影响其他流。  

### 与 TCP 的关键差异
| 维度 | TCP | QUIC |
| --- | --- | --- |
| 底层 | 直跑 IP（协议号 6） | 跑在 UDP 之上 |
| 队头阻塞 | 全局：一个包丢全连接卡 | 按流：仅该流卡 |
| 连接标识 | 四元组（含 IP） | 连接 ID（与 IP 解耦） |
| 握手 | TCP + TLS 多次 RTT | 融合握手（0/1-RTT） |
| 加密 | 可选、头部明文 | 内置 TLS 1.3、包头加密 |
| 演进 | 改内核、慢 | 用户态、快 |

### 注意的边界
`1`**单连接集中风险仍在**：cwnd、RTT 估计仍是全连接共享，整条连接降速时所有流都受影响。  
`2`**UDP 单包丢失仍影响该包内帧**：一个 QUIC packet 丢了，里面承载的帧都要等重传，只是 packet 轻量、影响面远小于 TCP。  
`3`**用户态 CPU 开销更高**：加解密与协议处理在用户态完成，比内核态 TCP 占 CPU，换来了灵活与可演进。  
`4`**NAT 对 UDP 映射超时更短**：长连接需靠 QUIC 自身保活/连接 ID 维持。  

`呼应`：以上机制正对应前文 HTTP/3 解决的三个痛点，并与上一篇 FAQ 的四元组、TIME_WAIT、HPACK 等概念相连。


## 补充
### https和http对比
`1`**本质区别**：HTTPS = HTTP + TLS（传输层安全），在 HTTP 之下、TCP（或 QUIC）之上加了一层加密。HTTP 是明文，HTTPS 是密文。  
`2`**端口**：HTTP 用 80，HTTPS 用 443。  
`3`**安全三件套**：加密（防窃听）、完整性校验（防篡改）、服务端证书（防中间人冒充）；HTTP 三者皆无。  
`4`**性能代价**：HTTPS 多了 TLS 握手，但现代硬件加解密开销极小，且 HTTP/2、HTTP/3 的 0/1-RTT 已把握手延迟压到很低（呼应前文 QUIC 0/1-RTT）。  
`5`**现实约束**：浏览器把 HTTP 标为「不安全」，Service Worker、绝大多数浏览器的 HTTP/2 都要求 HTTPS，搜索引擎也偏好 HTTPS。  

| 维度 | HTTP | HTTPS |
| --- | --- | --- |
| 传输 | 明文 | TLS 加密 |
| 端口 | 80 | 443 |
| 身份验证 | 无（易遭中间人冒充） | 证书验证服务端身份 |
| 完整性 | 无 | MAC 校验防篡改 |
| 握手开销 | 无 | 有 TLS 握手（0/1-RTT 缓解） |
| 浏览器 | 标记「不安全」 | 显示安全锁 |

### TLS的发展
`1`**SSL 时代（已废弃）**：SSL 1.0 未发布；SSL 2.0（1995）、SSL 3.0（1996）均因严重漏洞（如 POODLE）被废弃。如今「SSL」只剩口语习惯，协议层面应统称 TLS。  
`2`**TLS 1.0 / 1.1（已废弃）**：1999 / 2006 年（RFC 2246 / 4346），因不支持现代加密套件、易受降级攻击，已于 2020 年前后被主流浏览器禁用。  
`3`**TLS 1.2（长期主力）**：2008 年 RFC 5246，支持 AEAD、SHA-256，长期是部署最广泛的版本，至今仍常见。  
`4`**TLS 1.3（现代标准）**：2018 年 RFC 8446，重大简化与安全强化——  
　- 握手从多轮降到 **1-RTT**，会话恢复可达 **0-RTT**（这正是前文 QUIC 0/1-RTT 的基础，因为 QUIC 内建的就是 TLS 1.3）；  
　- **强制前向安全**（默认 ECDHE），移除静态 RSA 密钥交换、RC4、MD5、SHA-1、CBC 等不安全组件；  
　- **加密握手过程**（除必要明文），防窥探/篡改；  
　- 加密套件精简为仅 AEAD（AES-GCM、ChaCha20-Poly1305）。  
`补充`实际部署里：HTTP/2 在浏览器端几乎只在 HTTPS 上跑（h2 多要求 TLS）；HTTP/3/QUIC 更把 TLS 1.3 直接内建进传输层，没有「明文 QUIC」。所以「上 HTTPS」已是从 1.1 到 3 演进的隐形前提；它也和 QUIC 的连接迁移、按流可靠一起，构成 HTTP/3 弱网友好的基础。  

### TLS过程
`总思路`TLS 用 **非对称加密协商 + 对称加密传输**：非对称算法（ECDHE）只用来「安全商量」出一把只有双方知道的对称密钥，之后所有 HTTP 数据都用这把对称密钥加密——因为对称加密（AES 等）远快于非对称。  

`握手（以 TLS 1.3 为例，1-RTT）`
`1`**ClientHello**：客户端发支持的版本、密码套件、临时公钥（ECDHE key share）、随机数。  
`2`**ServerHello + 证书**：服务端选套件，回自己的临时公钥、随机数，以及证书（含服务端公钥 + 域名）。  
`3`**密钥交换（ECDHE）**：双方用各自临时私钥 + 对方临时公钥，算出**同一个共享秘密**；即便握手包被截获，无私钥也算不出，即**前向安全**。  
`4`**派生会话密钥**：由共享秘密 + 随机数派生出相同的对称会话密钥（加密密钥、IV 等）。  
`5`**Finished**：双方互发加密的 Finished 验证握手完整性，握手完成。  

`身份认证（防中间人）`客户端用内置信任的根 CA 公钥验证证书链签名、域名、有效期，确认对面是真服务端，并从中取公钥用于密钥交换；没有这步攻击者就能冒充服务端窃听。  

`握手后如何加解密（记录层）`
`1`**分片**：HTTP 报文切成 ≤16KB 的 TLS 记录。  
`2`**加密 + 完整性（AEAD）**：用对称密钥（AES-GCM / ChaCha20-Poly1305）加密数据并附认证标签（MAC），同时保机密与防篡改。  
`3`**加记录头**（类型 / 版本 / 长度，明文）交给 TCP；接收方读记录头、按长度取记录、用同一对称密钥 AEAD 解密并验标签，通过才交应用层。  

`常见误解`数据并非用「证书里的 RSA 公钥」加密；证书公钥只做身份认证，数据用协商出的对称密钥加密（对称快、且 ECDHE 前向安全，避免私钥泄露致历史流量被解密）。  

`呼应 0-RTT`之前握过并缓存密钥（PSK），重连时客户端直接发 0-RTT 数据（旧密钥加密），服务端用旧密钥解密——快但可重放（呼应前文 QUIC 0/1-RTT）。  

### TLS1.2和TLS1.3过程的不同
TLS 1.3 相对 1.2 在握手过程上的核心差异：**更少往返、更早加密、套件更安全、支持 0-RTT**。

| 维度 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 握手往返 | **2-RTT**（ServerHello → 证书 → ServerKeyExchange → ServerHelloDone → ClientKeyExchange → ChangeCipherSpec → Finished） | **1-RTT**（ClientHello 即带 key share，ServerHello 确定密钥后立即发 Finished） |
| 密钥交换 | 支持 RSA 静态密钥交换（**无前向安全**）+ ECDHE 等 | 仅 ECDHE / DHE（**强制前向安全**），移除静态 RSA |
| 握手是否加密 | 握手大部分**明文**（证书、ServerKeyExchange 等明文），到 ChangeCipherSpec 后才加密 | 从 ServerHello 之后**握手即加密**（证书、Finished 等密文） |
| 会话恢复 | Session ID / Ticket，恢复仍需 1-RTT | PSK，重连可达 **0-RTT** |


## 名词解释
`QUIC`:基于 UDP 的传输层协议（HTTP/3 的底层），把可靠传输、多路复用、拥塞控制搬到 UDP 之上，并用连接 ID 解决 TCP 队头阻塞与迁移问题，握手融合加密（常 0/1-RTT）。  
`TLS`:传输层安全协议，为 TCP（及 QUIC）提供加密、身份验证与完整性校验，前身是 SSL；HTTPS = HTTP + TLS。  
`0-RTT`:0-RTT：重连时客户端用之前缓存的密钥"零往返"直接带上数据发送，省去握手等待，但有重放攻击风险。    
`1-RTT`:1-RTT：QUIC 首次连接时把传输握手与 TLS 密钥协商合并为一次往返完成建连（比 TCP+TLS 的多次往返更快）。  


## FAQ

### http/2中的静态+动态字典是什么
#### 静态字典
协议预置 61 个最常见的头字段/值（如 :method: GET、:status: 200、content-type、server 等），直接用索引号代表，不必传原文。
#### 动态字典
本次连接中新出现的头部字段，会被缓存进两端各自维护的动态表；之后同一个连接里再出现，就用索引号引用，越传越省。它是连接级状态，客户端和服务端各持一份、保持同步。连接断开，动态字典刷新。
### 如何认识TCP 四元组绑定，IP 变就断和用连接 ID 标识，切网不断连
`1`TCP 连接由四元组唯一标识：一条 TCP 连接由（源 IP、源端口、目的 IP、目的端口）唯一确定。内核维护连接表，数据包到达时提取四元组查表，命中才认作这条连接上的合法数据。  
`2`IP 一变，四元组就变，连接即失效：客户端从 WiFi 切到 4G、或换网络使源 IP 改变，新包四元组（尤其源 IP）和旧连接对不上；对端按新四元组查表查不到，当成无归属包回 RST 或丢弃，原连接实际已断，需重新握手。  
`3`TCP 为什么做不到「IP 变了还不断」：TCP 头里只有端口，IP 来自网络层；协议本身没有独立于 IP 的「连接标识」字段，连接语义等价于「这两个 IP:端口 之间的会话」，IP 一变就不再是同一端点。  
`4`现实代价：移动端切网络时，正在跑的 TCP 长连接（HTTP/2、SSH、数据库、WebSocket）会立刻断，重连要重新握手，且连接级状态（如 HPACK 动态字典）也一并清空。    
`5`QUIC 用连接 ID 解绑：QUIC 在 UDP 之上引入 Connection ID，数据包用连接 ID 而非四元组关联连接；客户端 IP/端口变了，只要带相同连接 ID，对端仍认出是同一条逻辑连接，实现「连接迁移」，切网不断连（呼应上文 HTTP/3 用连接 ID 标识）。
### 目前计算机世界http1.1,http/2,http/3的使用情况
#### HTTP/2（主力）：
公开 Web 流量过半，主流站点、CDN、浏览器默认协商的就是它。多路复用 + HPACK 的收益在绝大多数场景已经够用。
#### HTTP/1.1（瘦死的骆驼）：
占比 ~28% 几乎不是"人用的浏览器"，而是 bot 爬虫、数据中心/服务器间 API 调用、遗留客户端撑起来的。浏览器侧早已以 2/3 为主；同时它仍是协商失败时的终极 fallback——任何新协议都保留 1.1 兜底，所以它不会真正消失。
#### HTTP/3（增长见顶）：
约 21% 流量，且全年只动了 0.54pt，已进入平台期。它在大厂（Google、Meta、Cloudflare、Apple）和移动端/高丢包网络收益明显，但前提是服务端放通 UDP 443、QUIC 栈成熟，部署门槛高于 2。
