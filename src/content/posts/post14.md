## Linux 常见文件系统介绍

### inode（索引节点）
文件在磁盘上的"身份证"，存储文件的**元信息**（类型、权限、所有者、大小、时间戳、数据块位置），**不含文件名**。文件名存在于目录项中，由"文件名 → inode 号"映射。一个文件对应一个 inode，对文件的所有操作最终都落到 inode 上。  
#### ext4 的特点
- 格式化时**预分配 inode 表**（按"分区大小 / 比例"算出总数），默认每个 inode 256 字节
- 数据定位：**extent 树**（"起始块 + 长度"描述连续区，元数据更紧凑，若数据分散在不同块则可以用树来维护）。
- 支持**内联数据**：极小文件的数据块直接塞进 inode 体，节约时间。
- 隐患：inode 预分配用完，即使磁盘有空间也建不了新文件。
#### xfs 的特点
- inode **动态分配**，不集中预建表，而是分布在各**分配组**中，由 B+ 树管理，扩展性极强，几乎不会"inode 耗尽"。
- 同样用 B+ 树组织 extent，大文件寻址高效。
- 无预分配上限问题，更适合海量小文件场景。

### 硬链接与软链接（inode 的直接推论）
| | 硬链接 `ln a b` | 软链接 `ln -s a b` |
| --- | --- | --- |
| 本质 | 目录项新增一条"文件名 → 同一个 inode"的映射 | 新建一个**独立 inode**，内容存的是目标路径字符串 |
| inode | 与源文件**同一个** | **自己的** |
| 删除源文件 | 数据还在（inode 链接计数减到 0 才真正释放） | 变成悬空链接（dangling） |
| 跨文件系统 | 不行（inode 号只在单个文件系统内唯一） | 可以 |
| 指向目录 | 不允许（防止目录树成环） | 允许 |
| `ls -l` 大小 | 与源文件相同，链接数 +1 | 等于路径字符串长度 |

生产用途：硬链接做同分区去重备份（`rsync --link-dest`）、软链接做版本切换（`/opt/app → /opt/app-v1.2`）。

### 超级块（superblock）
文件系统的"总目录"，记录整个文件系统的**全局元信息**：总块数、总 inode 数、空闲块/inode 数、块大小、魔数（文件系统类型标识）、挂载状态、日志位置等。挂载（mount）时内核先读超级块以识别类型并构建内存中的 `super_block`；超级块损坏则文件系统无法挂载，故通常有多份冗余备份。
#### ext4 的特点
位于**块组 0**起始为主超级块，并在多个块组中有备份
#### xfs 的特点
- 位于 **块组 0** 开头为主超级块，其余每个块组各有备份。

### 分区（partition）
磁盘上划分出的连续块区间，一个分区格式化化为**一种文件系统**，拥有独立的一套超级块、inode 表、数据块。分区是容器，文件系统是内部组织方式；mount 的本质即把某分区的文件系统根嫁接到目录树节点。  
#### ext4 的特点
- 把分区切成多个**块组（block group）**，每组含自己的inode 位图，块位图、inode 表、数据块。
- 块组化让元数据靠近数据，减少寻道（因为当一个文件被修改时，ext4会尽量把它的各种信息写到该文件系统所在块组）；超级块与备份分布在块组 0 及若干块组。
- ext4可以支持分很多个区
#### xfs 的特点
- 把分区切成多个**分配组**，每组是自治的"子文件系统"，各自管理空间与 inode，可**并行分配/查找**，天然多核友好。
- 多分配组结构带来高并发优势，但代价是不支持缩容。
- xfs分区数量按磁盘大小定，通常和 CPU/核心数相关。

### ext4和xfs使用场景
综上，ext4文件系统兼容性好，中小负载稳，极端高并发元数据或超大单文件时，受全局协调瓶颈，上限不如 xfs。  
xfs的分区是并发架构，在高并发场景下表现好。

### 读取某一个文件内容的过程，例如 cat /usr/test.txt
根 inode (/) 的数据块
  → 找到 "usr" 对应的 inode 号 → 取出 usr 的 inode（它是个目录）
usr 的 inode 的数据块
  → 找到 "test.txt" 对应的 inode 号 → 取出 test.txt 的 inode（它是个普通文件）  
然后vfs读他的元信息，例如权限，大小，数据块位置。内核根据extent树算出这个文件占用了哪些数据块，向块设备发送读请求，把数据块内容读进页缓存（page cache）。VFS 把页缓存里的数据通过 read 系统调用返回给 cat，显示出来。
**vfs**: 虚拟文件系统，是 Linux 内核里的一层统一抽象层，让所有不同类型的文件系统（ext4、xfs、proc...）都能用同一套接口接入，用户态的程序不用关心底层到底是哪种。  

## 文件挂载
挂载（mount）= 当前目录树的挂载点重定向到另一个文件系统的根inode
- 挂载点目录原本若有文件，挂载期间看不见，被新文件系统遮住。
- 卸载（umount）后原内容恢复——数据没丢，只是被盖住了。
- 所以挂载点一般选空目录。
| 类型 | 例子 | 本质 |
| --- | --- | --- |
| 普通挂载 | `mount /dev/sdb1 /mnt` | 嫁接一个新文件系统根 |
| 伪文件系统 | `mount proc proc /proc` | 无块设备，内核动态生成（proc/sysfs/tmpfs） |
| 绑定挂载 MS_BIND | `mount --bind a b` | 不换文件系统，给同一 inode 再建一个路径入口（可目录可文件） |
| 联合挂载 overlay | `mount -t overlay overlay -o lowerdir=/l1:/l2,upperdir=/u,workdir=/w /merged` | 多层目录（只读 lower + 可读写 upper）叠加成统一视图，靠 CoW 和白障实现复用与隔离（Docker 用） |

## 虚拟文件系统（伪文件系统）
`/proc`、`/sys`、`/dev` 这些目录，在 `lsblk` 里找不到任何对应的分区，`df -h` 却把它们列出来。它们就是**虚拟文件系统**：没有块设备、没有磁盘上的超级块和 inode 表，整棵目录树是内核在内存里现造的。
### 为什么能"虚拟"：VFS 只要求接口，不要求磁盘
VFS 注册一个文件系统时，只要求实现几组回调（`lookup`、`read`/`write`、`readdir`、`stat`），**从不检查数据是不是来自磁盘**。所以内核可以注册一个"假"文件系统：inode 在内存里现造，`read()` 时不发块设备请求，而是**直接调用一段内核函数，把内核结构体里的字段拼成字符串返回**。
判断标准一句话：**内容不是"存"出来的，是"算"出来的**。`cat /proc/meminfo` 每次读都是内核现场统计，磁盘上没有任何一个块存着这个文件。
#### /proc：进程和内核状态的窗口
```bash
ls /proc/<pid>/           # 一个进程一个目录，内容来自 task_struct、mm_struct
cat /proc/<pid>/status    # 状态、内存、线程数
cat /proc/<pid>/stat      # 第 14/15 字段是 utime/stime，CPU 使用率就从这儿算
ls -l /proc/<pid>/fd      # 进程打开的所有文件，都是指向真实 inode 的符号链接
ls -l /proc/<pid>/root    # 进程眼中的根目录——容器里这个链接就指向 overlay 的 merged
ls /proc/<pid>/ns         # 该进程所属的各命名空间
```
- 为什么虚拟：进程随时生灭，`/proc/meminfo` 每次读都是现场统计，磁盘上不可能预先存一份"当前内存用量"。
- 可写的那部分就是 sysctl：`echo 1 > /proc/sys/net/ipv4/ip_forward` 等价 `sysctl -w net.ipv4.ip_forward=1`；容器里改的是自己 net ns 的副本，宿主机不受影响。
- 生产坑：`/proc/cpuinfo`、`/proc/stat`、`/proc/meminfo` **不跟随 PID / CPU namespace**，容器里 `top` 看到的是宿主机 CPU——这就是容器 CPU 使用率要单独算的原因。
#### /sys：设备与内核对象的结构化模型
sysfs 把内核内部的对象直接导出成目录，**一个属性文件对应一个内核变量**：读 = 调驱动的 `show()`，写 = 调 `store()`。
```bash
cat /sys/class/net/eth0/address         # MAC 地址
cat /sys/block/sda/queue/scheduler      # IO 调度器，可写切换
echo 1 > /sys/block/sdb/device/delete   # 热拔盘（生产换盘的标准动作）
cat /sys/fs/cgroup/memory.max           # cgroup 的限制，本质也是 sysfs 属性
```
#### /dev/fuse：一个字符设备，不是文件系统
`/dev` 目录本身是 devtmpfs（设备注册时内核自动建节点），但**里面的节点是设备，不是文件**。`ls -l /dev/fuse` 看到 `c 10, 229`：主 / 次设备号是驱动注册表里的索引，`open/read/write` 它等于调 FUSE 内核模块的回调，而不是读磁盘。
它是用户态文件系统的入口：进程 `open("/dev/fuse")` 拿到一个 fd，mount 时把这个 fd 交给内核，之后该挂载点的所有 IO 都由内核打包成请求、经这个 fd 交给用户态进程处理。sshfs、s3fs、JuiceFS、fuse-overlayfs（rootless 容器）能存在，靠的就是这套机制——完整的原理、性能与排障见下一章。
#### tmpfs：不算"纯虚拟"，但也没落盘
tmpfs 有真正的 inode 和数据页，只是页只存在内存（可换出到 swap），`df -h` 的大小约等于可用内存，重启即失。`/run`、`/dev/shm` 都是它。
- 生产坑：容器 `/dev/shm` 默认只有 64MB，Chromium、Python 多进程共享内存之类的程序会莫名崩溃，需要 `--shm-size` 调大。

## FUSE：把文件系统搬到用户态

### 存在作用：为什么需要 FUSE
一句话：**它把"实现一个文件系统"从内核开发变成普通应用开发。**

没有 FUSE 时，想给系统加一种新文件系统（数据在对象存储上、透明加密、压缩后落盘），只有两条路：**写内核模块**（C 语言、跟着内核版本走、一个空指针就 panic 整机），或者**让每个应用自己适配**（等于放弃 POSIX 语义）。FUSE 给出第三条路：**内核只保留一层转发**，真正的 `lookup/open/read/write/readdir` 由用户态 daemon 实现。

由此得到的能力：
- **零内核改动**：压缩、加密、去重、版本化、对象存储语义都在用户态拼装，发布节奏跟应用走，不受内核版本和发行版约束。
- **叠加层**：不必重写底层，就能在现有文件系统之上叠一层（加密层、审计层、镜像层）。
- **微内核化方向**：把非核心能力从内核移到用户态，内核只保留最小职责——FUSE 是这条路线最成功的实践之一。

代价同样明确：**每次 IO 都要穿两次内核边界**。所以选型原则一句话：**FUSE 用来解决"本地盘没有这个能力"，不用来解决"本地盘不够快"。**

### 工作流程（以 rootless BuildKit 为例）
分两步：先挂载注册，再逐次转发 IO。用 **rootless 模式的 BuildKit** 走一遍最直观。

**第一步，挂载注册。** 普通用户拿不到初始 user namespace 的 CAP_SYS_ADMIN，直接挂内核 overlayfs 会失败，所以 rootless 的 buildkitd 由 rootlesskit 放进 user namespace，存储层改用 fuse-overlayfs：snapshotter 需要把 lower/upper/work 三组目录叠成一个视图，于是由 fuse-overlayfs 进程打开 `/dev/fuse` 拿到 fd，再以这个 fd 完成挂载。内核随之建立一条 FUSE 连接，这个挂载点下的所有路径操作都记在这条连接名下，内核不再亲自处理。这里要分清角色：**真正的常驻 daemon 是 buildkitd**，fuse-overlayfs 只是按需拉起、卸载即退的服务进程；但只要它死了，挂载点照样卡死。

**第二步，一次读请求的往返。** 某个 RUN 步骤里，编译器去读源码文件：

```text
编译器 read() → VFS → fuse 内核模块
                 → 请求打包进这条连接的队列（挂在 /dev/fuse 上）
                 → fuse-overlayfs 从 fd 取走请求
                 → 它在用户态判断文件在 upper 还是 lower 层，再去对应目录读
                 → 把结果写回 fd → 内核唤醒编译器
```

- VFS 只认接口、不关心实现跑在内核还是用户态——这就是一个普通进程能"造"出文件系统的原因。
- **每个操作都是一次完整往返**：`open`、`stat`、`readdir`、`read` 各算一次。构建场景里 `RUN npm install`、解压依赖动辄几万个小文件，每个文件都要走一次 `lookup` + `getattr` 往返——这就是 rootless 构建比内核 overlayfs 慢一截的直接原因。

### 性能：主要代价在哪
| 环节 | 开销来源 |
| --- | --- |
| 上下文切换 | 每次 IO 至少两次用户态 ⇄ 内核态往返，加请求/响应两次队列拷贝、加 daemon 调度延迟 |
| 元数据放大 | 单个 syscall 变成一次跨边界往返，小文件密集时被成倍放大 |
| 缓存责任转移 | 内核 page cache 只剩很薄一层，命中率主要靠 daemon 自建的本地缓存目录 |

## 生产运维：扩容、缩容与常见故障
### LVM：多盘池化与在线伸缩
整个分层过程就是一层层把裸盘"包装"成逻辑设备：
```text
裸盘 /dev/sdb          pvcreate    PV（物理卷）
PV                    vgcreate    VG（卷组，把多块盘拼成一个资源池）
VG                    lvcreate    LV（逻辑卷，从池里切一块）
LV                    mkfs + mount 文件系统 + 挂载点，用户真正看到的目录
```
- 扩容时 `lvextend` 把 LV 撑大（池里还有空间就行），再 `xfs_growfs`/`resize2fs` 扩文件系统，全程在线；
- 换盘时 `pvmove /dev/sdb` 把数据从旧盘搬到新盘，`vgreduce` 摘掉旧盘，业务不中断——这是 LVM 最大的价值。
- 代价是 `df` 与磁盘之间多了一层映射，排障要按 `pvs → vgs → lvs` 逐层查。

**为什么不用它做备份**：LVM 快照是 CoW（写时复制）的——快照建立后，源卷**每写一个块**，旧内容先复制进快照空间，原块才被改写。所以快照不是"独立副本"，而是挂在源卷上的差量：
1. **源卷写入越多，快照空间消耗越快**，打满后快照直接失效，数据保护随之消失——日志盘上挂快照，几个小时就可能写满；
2. **拖垮性能**：每次源卷写入都多一次复制 IO，写入越密集越明显，等于给业务加了个隐形负担；
3. 源卷损坏时，快照只有旧数据+差量，**恢复点不可控**。
一句话：快照解决的是"几分钟前的状态回滚"，不是备份——备份要有**独立于源卷的完整副本**（云快照/存储层复制/备份软件，且异步落别处）。

**云原生场景基本不用 LVM 了**：容器平台的存储诉求是"动态供给 + 跨节点共享 + 随 pod 漂移"，LVM 是单机本地块设备池化，做不到网络共享，也不便与 CSI 对接。现在主流做法是云盘直接挂载（`local-path`/`hostPath` 类 CSI 驱动）或对接分布式存储（Ceph/Rook、NFS、云厂商块存储），扩容走 CSI `VolumeExpansion`，快照走存储侧 `VolumeSnapshot`——LVM 只在传统物理机本地盘管理里还有一席之地。

### 文件系统选型：默认就好，别瞎改
- **发行版默认 ext4，就别改成 xfs**：默认配置是发行版社区和内核团队验证过的最稳组合，fsck 工具链、内核参数、故障案例全按它适配；换个文件系统等于主动引入未知变量。
- **根盘 IO 压力本来就低**：系统盘只跑内核、systemd、少量服务和日志，读写量远小于业务盘，ext4 的全局协调瓶颈根本碰不到，稳和兼容才是它的主场。
- **业务数据卷一般都用 xfs**：数据盘才是高并发、大文件、海量小文件的主战场，xfs 的分配组并行架构吃满多核，动态 inode 也不会"空间还在却建不了文件"。
- **业务一般不缩容，顶多迁移数据**：缩容 = 停机搬数据 + 文件系统风险，生产里几乎清一色"涨了就扩、或者整卷迁到新盘"，没人反着做——所以 xfs 不支持缩容压根不是短板

### 大部分场景直接用裸盘，只有系统盘才分区
云盘、数据盘基本都是**一块盘 = 一个分区**（甚至不分区直接 `mkfs`），只有系统盘会切成 `/boot`、`/`（+ swap/EFI）。原因：
- **分区的价值在"一盘多用"**：早年一块大盘要塞系统 + 数据 + swap，才需要切区做隔离；现在云盘按需购买，系统盘、数据盘、日志盘各自独立下单，一块盘只干一件事，再分区纯属多余。
- **分区反而添乱**：分区表是固定边界，扩容时还得动它，多一层出错点；不分区直接格式化，`lsblk` 与 `df` 一一对应，排障干净利落。
- **系统盘必须分区**是启动的硬性要求：`/boot` 要独立放内核、initramfs、GRUB，避免根分区写满导致系统起不来；EFI/swap 也需要独立的分区类型标识，引导固件才认。

### 磁盘满了，du 加起来对不上df
现象：`df -h` 显示 100%，把目录下所有文件 `du -sh *` 加一遍却少好几个 G——空间到底被谁吃了？
**原因 1：文件已删除，但进程还开着 fd**
`rm` 只删目录项（"文件名 → inode"映射），不等于释放数据块：只要还有进程握着这个文件的 fd，内核就继续算它占着空间。这时 `du` 没法看见它（已经没有目录项可遍历），`df` 却照算不误——差值就是这些"幽灵文件"。生产最典型的就是日志：logrotate 切完日志，应用还握着旧文件句柄没 reopen，`rm` 掉的 GB 级日志一直不释放，磁盘越跑越满。
```bash
lsof +L1                               # 找 link count 为 0 的已删除文件
```
**原因 2：容器里 du 和 df 本身就对不上**
容器内 `df -h /` 看到的是**宿主机底层文件系统**的容量（overlayfs 直接上报 upper 所在盘的总数），而 `du` 统计的只是本容器 upper 目录的可见文件——别的容器、镜像层、宿主机自身写入都算在 `df` 里却不进你的 `du`。所以容器里永远"du 加不满 df"，排查 `/var/lib/docker` 写满要**在宿主机上查**

### 磁盘还有空间但是无法创建文件
现象：`df -h` 还有富余，但无法创建文件，**耗尽的不是空间，是 inode**。
根因在前文 inode 机制：ext4 格式化时按分区大小**预分配固定数量的 inode 表**，每个文件（哪怕 0 字节）都要占一个 inode。海量小文件场景（把 inode 抽干后，磁盘块再空也建不了新文件——这是 ext4 的结构性隐患，xfs 动态分配 inode 则几乎不会遇到。
```bash
df -i /data                            # IUse% 100% 就是它；File 一列是 inode 总数
find /data -xdev -type f | wc -l       # 定位哪个目录文件数爆炸
# 处理：清理小文件目录；建文件系统时调大 inode 比例（-i 选项）；长期海量小文件直接换 xfs
```

### 文件系统变成只读
现象：`touch` 报 `Read-only file system`，业务全部写失败。如果不是权限问题，就是**文件系统自己切了只读保护数据**。
```bash
#打印内核环形缓冲区（kernel ring buffer）里的日志
dmesg -T | grep -iE 'ext4|xfs|I/O error|remount'   # 找第一现场：IO 错误或元数据损坏
```
- **触发机制**：ext4 默认 `errors=remount-ro`——检测到元数据错误或底层 IO 失败，立刻把挂载切成只读，宁可停写也不让损坏扩大；xfs 更激进，可能直接 shutdown，之后连挂载都不可用。
- **根因大多是底层存储链路问题，不是文件系统**：云盘抖动/掉盘、宿主机内核 bug、RAID/存储链路故障、云厂商维护事件——文件系统只是"报警器"。**先查 `dmesg` 和云厂商事件日志**：底层故障没排除就强行恢复读写，会让损坏扩大。
- **修复姿势总结**：排查优先看 dmesg 和云厂商事件，修复前务必快照，禁止直接强行 remount,rw。

## 补充
### 数据恢复原理
数据恢复能够在一定时间内找回"已删除"文件，根本原因在于：**磁盘上的数据从来不是被真正删除的，而是被覆盖。** 当你强制删除某个文件时，系统并没有把数据块里的 0/1 清零，而只是**切断了文件与对应数据块之间的联系**——也就是释放了 inode 对该数据块的指向。  
结合前文 inode 机制，具体过程如下：
- **删除的本质是"断链"**：删除操作（如 `rm`）只是移除目录项中的"文件名 → inode 号"映射，并把 inode 标记为空闲、将其 extent 指向的数据块归还给"空闲块位图"。数据块里的内容**原封不动地留在磁盘上**，直到被新文件写入覆盖。
- **联系未断之前数据可见，断链之后仍物理存在**：文件在目录树中"消失"≠ 数据消失。只要那些数据块还没被别的文件占用并改写，原始字节就一直躺在原地。
- **恢复的原理是"重建联系"**：数据恢复工具扫描磁盘，找到仍被数据块占用但已无目录项引用的"孤儿 inode / 游离数据块"，根据文件特征（文件头魔数、结构签名）识别其类型，重新建立"文件名 → inode → 数据块"的映射，从而使文件重新可见。
- **时间窗口由"覆盖"决定**：恢复的可行性完全取决于"被删除的数据块是否已被新数据覆盖"。删除后越早恢复、且磁盘写入越少，成功率越高；一旦数据块被新文件写入（覆盖），原内容便不可逆转地丢失——这也是为什么误删后第一件事是**停止向该分区写入**，而非继续操作。
一句话：**删除只是解除了文件到数据块的指针，数据本身要等被新内容覆盖才会真正消失；数据恢复，就是赶在覆盖发生前把这条联系重新接上。**  
### 磁盘分区表
分区表是写在磁盘最开头的"地图"，记录这块盘怎么分、分了几块。两种格式：
| 特性 | MBR | GPT |
| --- | --- | --- |
| 最大磁盘容量 | 2TB（受寻址位宽限制） | 18EB（几乎无上限） |
| 最大分区数 | 4 个主分区（超出需用扩展分区+逻辑分区，较麻烦） | 默认 128 个（可配置更多） |
| 冗余备份 | 分区表仅一份，损坏即全盘不可用 | 头尾各存一份分区表，可恢复 |
| 启动方式 | 传统 BIOS | 现代 UEFI |
| 完整性校验 | 无 | 有 CRC 校验，可检测损坏 |
> 结论：现代服务器、云主机、大于 2TB 的磁盘一律使用 GPT；MBR 仅用于老机器或小容量盘。
**CRC校验** ：发送方/写入方根据数据算出一个短校验值（CRC 值），接收方/读取方用同样算法再算一遍，比对不一致就说明数据坏了。（适用于GPT分区表，网络包等）
bios和UEFI都是写在主板芯片上的固件，是电脑通电后执行的第一个程序，负责：  
- 通电自检（POST）：检查 CPU、内存、显卡等基本硬件是否正常。
- 找到启动设备（硬盘/U盘）。
- 把控制权交给硬盘上的引导程序（bootloader），由它加载操作系统内核。
### linux启动过程
1. BIOS/UEFI    → 硬件自检,找引导设备
2. Bootloader   → GRUB 加载内核 + initramfs（初始内存文件系统吗，是 Linux 启动过程中,内核加载的一个临时小根文件系统（因为将磁盘挂载到根文件需要一些磁盘驱动，比如RAID,LVM，所以需要一个临时的根文件系统）,存放在内存里。）
3. 内核         → 初始化硬件,挂载真实根文件系统
4. systemd      → PID 1（用户态祖先进程）,并行启动各类服务
5. 登录界面     → 系统可用
